# Alta de envíos (RF-01 y RF-02)

`POST /api/shipments` registra solicitudes para administradores habilitados y clientes con cuenta y ficha habilitadas. El cliente solo puede operar sobre la ficha asociada a su solicitud aprobada. La API vuelve a verificar identidad, rol y estado dentro de la transacción; una dirección habitual debe estar activa y pertenecer al cliente. Como alternativa se acepta una dirección nueva, que puede guardarse como habitual en la misma transacción.

Por decisión del equipo, para este incremento se requieren cliente, destinatario, teléfono del destinatario, descripción del paquete y dirección completa de retiro y entrega. Fecha de retiro y observaciones son opcionales. Los datos de contacto del remitente se toman de la ficha del cliente. El identificador es generado por el servidor, el estado inicial es pendiente y el evento inmutable de creación registra actor, fecha y custodia inicial del remitente. Las direcciones se copian al envío para conservar el dato histórico.

Web y móvil permiten indicar una fecha y hora solicitadas de entrega y adjuntar un comprobante al crear el envío o después. El sistema exige que la fecha de entrega no sea anterior a la de retiro. La custodia inicial se guarda como `SENDER`; los registros anteriores conservan custodia desconocida, sin suponer que sigue en el remitente. El cambio de custodia y su historial operativo corresponden al ciclo posterior.

Desde el alta de envío, administración puede crear una ficha de cliente con el formulario habitual y continuar con ella. Si falla la lectura posterior al alta, se informa que el cliente sí fue creado y se permite buscarlo de nuevo. Un código completo con formato `OH-UUID` y sin otros filtros abre directamente el detalle permitido; los códigos parciales y las búsquedas combinadas conservan el listado. Un código inexistente o fuera del alcance del cliente no revela información del envío.

Los comprobantes se guardan en PostgreSQL dentro de la transacción que los vincula al envío, con usuario y fecha; su carga no confirma pagos. Se aceptan archivos PDF, PNG y JPG de hasta 5 MB, comprobando su firma inicial y tipo declarado. El acceso autenticado usa la misma restricción de propiedad del envío; se sirven como descarga y se registra la carga. La firma inicial no constituye un análisis antivirus ni garantiza que todo el archivo sea válido. Se admite un comprobante vigente; al reemplazarlo se conserva el anterior en una tabla de historial protegida contra cambios. Los respaldos de base de datos deben incluir los bytes actuales e históricos y comprobar su restauración.

La migración `202611210002_shipment_schedule_custody` solo se aplicó a bases de prueba aisladas. Antes del despliegue compartido se debe coordinar con el responsable de infraestructura y respaldar. Falta validación visual en dispositivos y con ZITADEL real; la obligatoriedad de datos y las condiciones de entrega deben revisarse con Fernando.

`GET /api/shipments` lista y filtra por código, nombre del cliente, destinatario, fecha de creación, estado, prioridad y responsable (este último solo para administración); `GET /api/shipments/:id` devuelve el detalle permitido. Los clientes solo ven envíos de su ficha habilitada y aprobada y no reciben observaciones internas ni responsables. El historial presenta a clientes únicamente eventos permitidos sin actor ni notas. Administración puede asignar o reasignar un repartidor activo y disponible, con historial y control de cambios concurrentes. Esta asignación básica no incluye planificación de jornada, custodia, ni vista de tareas del repartidor. Las pantallas web y móvil todavía requieren pruebas visuales y con identidad real.

La migración `202611210003_assignment_receipt_history` agrega la asignación y conservación de comprobantes anteriores. Se probó en PostgreSQL aislado; no se aplicó a staging ni producción. Coordinar el despliegue compartido y respaldo con infraestructura.

Verificación: `npm test`, build y pruebas con PostgreSQL aislado en `test/shipments.database.test.mjs` y `test/shipments.http.test.mjs`. Las pruebas de base y HTTP necesitan una base desechable cuyo nombre incluya `ohana_isolated_shipments`, con las migraciones aplicadas. No se modificaron bases compartidas ni se desplegó este cambio.
# Reintentos del alta

Web y móvil envían `Idempotency-Key` con un UUID v4 por cada intento de alta. Ante una respuesta incierta, conservan el mismo identificador y los mismos datos para reintentar; la API devuelve el envío previamente creado sin repetir el alta ni guardar otra dirección. El identificador corresponde al código `OH-<UUID>` mostrado para consulta si se abandona la pantalla. El reintento solo puede recuperarlo el usuario que lo creó y para el mismo cliente. Cada alta nueva requiere otro identificador. El encabezado es opcional para clientes anteriores, que no cuentan con esta protección. Si se cierra la pantalla antes de confirmar, hay que consultar el código antes de iniciar otra alta.
